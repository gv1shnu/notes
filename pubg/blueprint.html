Two kinds of number: synthetic facts vs real pipeline metrics

Synthetic gameplay facts

  • Kills: canonical player_eliminated facts per attacker, at namespace/run/match/player grain
  • Project score: kill_points × kills + placement points (editable by DB admin)
  • Rank: score DESC, wins DESC, kills DESC — per match; pick one match in Superset
  • Alive players: min alive count in each 10-second window (not sessions)
  • Server latency p95: percentile_cont(.95) over pooled synthetic samples per window

Measured pipeline metrics

  • Committed lag: broker end offset − Flink checkpoint-committed offset, per partition
  • Emitted-to-processed p95: processed_at − emitted_at over recent persisted rows
  • Persisted events/sec: Prometheus 1-min rate of the row-count gauge
  • Checkpoint duration / age: from Flink's REST checkpoint endpoint
  • Watermark: min operator input watermark (epoch ms)

the discipline of this project is keeping those two columns clearly labelled, so nobody reads a synthetic latency as a real SLA.

Dashboards authored in code

No chart is assembled by hand. superset/bootstrap.py creates the database connection, datasets and all 24 charts across four dashboards, so the BI layer is reproducible and reviewable in git (charts + dashboards are also exported as YAML under superset/assets/).

Live Leaderboard — ranks, kills, damage, placement (each row: provisional / final) Match Operations — running vs reconciled, alive players, eliminations over time, manifest completeness Server Health — latency p95, packet loss, CPU/mem, tick, injected incident windows labelled Pipeline Reliability — throughput, committed lag, processing delay, checkpoint duration

Freshness is polling, not push: Superset refresh is configured at 15 s. One live proof saw a new DB value appear in an auto-refreshing chart after 12.9 s — an observation, not a guaranteed SLA.
