The problem

I wanted to build, and be able to defend in an interview, a real-time analytics pipeline that stays correct when delivery is messy: out-of-order, duplicated, late and malformed events.

The scenario is a synthetic battle-royale game. Four independent event sources stream through Kafka → Flink → PostgreSQL and into four live Apache Superset dashboards. All gameplay/server data is synthetic; there is no PUBG affiliation. The pipeline metrics, though, are measured from real components.

Architecture

What makes it correct under messy delivery

  • Contracts first. Flink validates typed/versioned JSON contracts; malformed or wrong-version input is rejected to a dead-letter topic while valid input keeps flowing.
  • Dedupe by identity. Keyed deduplication with a 24-hour TTL; the first accepted identity wins. Repeated writes leave canonical counts unchanged.
  • Event-time, not arrival-time. Watermarks + idleness; bounded-late events are accepted, excessively late ones are retained and corrected.
  • Provisional → final. Results stay provisional until the immutable facts match the source manifest, then become final. "Finish-first / shuffled" data resolves correctly.
  • Recovers. With the Flink TaskManager killed mid-run, checkpoint-committed Kafka lag rose 108 → 553, then drained to zero after recovery, outcomes unchanged.
