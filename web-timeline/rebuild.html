How I judge it

  • Tier safety: a default run emits zero attack traffic; higher stages appear in the report as "skipped".
  • Completeness: CLI summary counts hosts, ports, HTTP endpoints, URLs, findings by severity, exploits, and loot.
  • Robustness: a missing tool or one stage's error never aborts the run.
  • Operator leverage: do the correlate insights point a human straight at the best lead?

Rebuild it from scratch

  1. Model first
    Write the dataclasses (Host, Service, HttpEndpoint, CrawlUrl, Finding, Exploit, Insight, Credential, Secret, Loot, StageRun) and ReconResults with to_json() and summary().
  2. Stage base class
    Stage.run(): check enabled → tier ≤ ceiling → tool present → execute() in try/except → finalize with timing. Write the gate before any real stage.
  3. Safe runner
    A runner.have(tool) check and a subprocess wrapper that takes an argument list, enforces a timeout, and writes .cmd/.stdout/.stderr.
  4. Passive stages
    subdomains, resolve, http_probe, crawl, screenshots, exploit-lookup — each parses its tool's output into the model.
  5. Orchestrator
    Ordered STAGE_CLASSES; run each; rewrite results.json after every one; render the Jinja report.
  6. Active + offensive tiers
    Add behind --active / --exploit, with config caps and opt-in flags for the most destructive actions.
  7. Correlate
    A passive stage reading the whole ReconResults and emitting Insights that each end in a human next-step.
  8. Front ends
    CLI (recon.py) and a Flask dashboard that wraps the Orchestrator in a thread and streams the log over SSE. Re-check the tier server-side.
