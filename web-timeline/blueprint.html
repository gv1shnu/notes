The pipeline (passive → active → correlate → offensive)

One typed result model

ReconResults ├ targets, active, offensive, started/finished ├ hosts[] Host(name, ips, cname, resolved, sources) ├ services[] Service(host, port, product, version) ├ http[] HttpEndpoint(url, status, title, tech, tls, screenshot) ├ crawl_urls[] CrawlUrl(url, source) ├ findings[] Finding(template_id, severity, cves[], exploits[]) ├ insights[] Insight(category, confidence, evidence, next_step) ├ credentials[] / secrets[] / loot[] └ stages[] StageRun(name, status, note, produced, timing)

Stages parse native tool output into these dataclasses. The aggregator, the JSON writer and the Jinja report all read the same objects, so adding a tool never ripples into the report.

results.to_json() is rewritten after every stage → crash-safe & resumable-by-hand.

Severity is an enum; summary() rolls up counts by severity for the CLI banner and dashboard.

The correlate stage (where the real value is)

Passive, no tools, no extra traffic. Six heuristics each emit an Insight that ends in an explicit human verification step, never an automated trigger:

insightsignal it fuses
subdomain-takeoverdangling CNAME fingerprinted against ~30 claimable third-party services
sensitive-exposurecrawled URLs matching VCS / env / backup / debug / admin / API-schema path patterns
injection-surfacequery-parameter names matching known risky conventions
exposed-serviceDB / management ports reachable, escalated when the host is also CDN-fronted (origin exposure)
shadow-itinternal-sounding hostnames (staging / CI / admin) live on the public internet
vuln-rolluphosts with ≥ 2 CVE findings rolled into one prioritized target + exploit-availability tally
