Data model & RPC surface

A release, start to finish

  1. Configure
    Instructor picks a section, question count and 1–120 s/question; UI shows nominal time = count × seconds, and the join URL.
  2. Go live
    The count × seconds duration is also the joining window. Students admitted inside it keep their timers afterward.
  3. Play
    Each accepted answer immediately serves the next question; unanswered ones advance from their original deadlines, even offline.
  4. Close
    Auto: admission closed + all started attempts finished. Or the instructor ends early (accepted answers kept, the rest become timeouts). Hard cap: 3 h.
  5. Reveal
    Only now do answers, explanations and scores unseal; students review saved answers; instructor sees the leaderboard + reports.

Scoring & the metrics it records

  • Correct = points; wrong & timeout = 0; score can't go negative.
  • Per student & round: correct/wrong/timeout counts, mean answering time, accuracy, and a strict half-time count.
  • Leaderboard materialises on submit; final reveal is gated until close.
  • Self-paced across all 9 rounds (migration 012); fixed A–E sections (013).

Built as an ordered migration stack

The whole backend is a sequence of numbered SQL migrations, applied in order — the feature history is the migration list:

Migration 008 is a protocol change: apply it between sittings and deploy the matching frontend with it. The old roster table is retained as legacy data, not an access control.

Client robustness

  • Serializes requests; retains uncertain submissions for identical retries; backs off failures.
  • Validates every response; ignores responses after unmount/sign-out.
  • Anchors visual time to server timestamps + performance.now().
  • Retries RPCs rejected for a future-issued token (clock skew).
