How I judge it

  • CI concurrency suite: 120 concurrent starts, duplicate submissions, instructor closure racing submissions — on a disposable Postgres 17.
  • verify gate: format + lint + tests + typecheck + production build, enforced by branch protection (a local hook alone can't).
  • Sealing: can any client read a correct answer before close? (No.)
  • Timing integrity: does a refresh / disconnect / clock skew ever extend a deadline? (No.)

Rebuild it from scratch

  1. Schema as migrations
    sessions → members → releases → frozen questions → runs → attempts, with RLS and revoked direct table access from the first migration.
  2. RPCs only
    Instructor: open/configure/go_live/end/report. Student: join/state/start/next/submit/result. Each locks the session and enforces membership + sealing.
  3. Server clocks
    Stamp an immutable deadline per question at start; compute expiry server-side; never trust the client's time.
  4. Sealing
    Keep answers/keys in a table the browser can't read; reveal only after the release closes.
  5. Client controller
    Serialize requests; identical-retry uncertain submits; back off; validate; anchor time to server + performance.now(); handle clock-skew rejections.
  6. Auth + roles
    Google OAuth; a before_user_created hook; an instructor email allowlist checked server-side.
  7. Tests + gate
    Real migrations in PGlite; a Postgres concurrency suite; a verify CI check required before deploy.
  8. Ship
    Static Vite build under a base path on Pages; auto-apply migrations from main; add the tempters last.
