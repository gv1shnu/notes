The problem

A browser multiplayer racing game: drive a procedural circuit with cockpit/hood/chase cameras, engine audio, lap timing, and a live leaderboard — up to 16 drivers in a room.

The interesting part isn't the car, it's the netcode: making other players' cars move smoothly over a lossy WebSocket while the server stays the authority on laps.

The networking model

What shaped it

  • Responsiveness vs. authority. Physics runs locally at 60 Hz so steering feels instant; the server validates and only broadcasts at 20 Hz, so it stays the source of truth for lap times.
  • Smoothing lossy snapshots. Peers are rendered ~100 ms in the past and interpolated between the last two snapshots, so jitter and drops don't make cars teleport.
  • Fair laps need invalidation rules. Leaving the track, respawning, reversing through checkpoints, or pausing the tab voids the timed lap.
  • Cars got stuck off-track. An early sticky wall was replaced with an off-track prompt + auto-respawn (and an R-to-respawn key).
  • No runtime CDN. The client bundles pinned deps into hashed dist/ assets, so a CDN outage can't break the game.

testing a multiplayer game

A soak test runs 60 local clients for 2 minutes; a race-recording harness drives 3 independent WebSocket clients with automated controls and separate racing lines to capture a real race on video.
honest status: a practice prototype — no car-car collisions, no server-owned physics, no touch/gamepad yet.
