Fan-out architecture

How results get ranked

score = w1 · squash(BM25(title, content)) + w2 · RRF(rank across engines) + priors(source trust, recency) BM25 Okapi over title+content (util/bm25.js) RRF Σ 1/(60 + rank) → agreement boosts a URL filter drop results sharing NONE of the query terms each signal squashed to [0,1] so scale can't dominate

If several engines independently surface the same URL near the top, RRF lifts it. BM25 handles term frequency, rarity and document length. Priors are gentle tie-breakers.

date sort streams (SSE, newest first, feels fast); relevance sort blocks because BM25+RRF need the whole set.

Smart routing: a deterministic classifier

Going wide is the default, but util/classifier.js can read a query and pick the fitting engines — pure rules (keywords, phrases, regexes), no ML, no network, so the same query always routes the same way. Opt in with ?route=auto.

The engines that fight back

  • Warm Python worker (ddg_worker.py + pyworker.js): the ddgs interpreter is kept alive over a thread pool, not restarted per search.
  • OSINT: Sherlock's real site DB ported to Node (util/sherlock.js), ~480 checks on a bounded pool (~10–25 s, some soft-404 false positives); domains → crt.sh subdomains.
  • SSRF guard on /api/resolve-date: public http(s) only, re-checked after DNS (rebinding-proof).
  • TTL cache so repeated queries skip the whole fan-out; parallel pagination for Wikipedia/arXiv/StackOverflow.
  • Metrics to metrics.jsonl: per-engine latency, counts, cache hits, filter trim; viewable at /stats.
