Backend modules

  • categories/ — REST with caching + pagination + sort
  • products/ — book detail, by handle (stable) or id (legacy)
  • scraper/ — scraper.service (nav/category/product), scraper.config (pagination, delays, retries), scraper.processor (Bull worker), wob-http
  • cache/ — Redis TTL layer
  • pdf/ — the Extract-PDF feature (search / download / inspect / match)
  • health/ — health checks (plus a keep-API-awake workflow for the free tier)

Extract PDF: matching by page count

The book page has an Extract PDF button: it queries SerpApi's Google engine for "Title" "Author" filetype:pdf, downloads up to five results, and parses each with pdf-lib — then matches by page count:

accept Pages / Page count / No. of pages … ("320 pages", "1,024") require BOTH a title and an author tolerance = max(5, ceil(expectedPages * 0.05)) inclusive → 320-page listing matches a 304–336-page PDF prefer the closest; stop on an exact match skip encrypted / broken / non-PDF / previews / out-of-tolerance cache the exact bytes 10 min; serve via /pdf/:token (never an arbitrary URL)

The frontend renders pages with PDF.js from a temporary blob URL (avoids source CORS/framing), with prev/next, zoom, and screen-reader text.

honest caveat shown to the user: a matching page count does NOT prove edition, completeness, or rights. Pagination is a heuristic.

No Google HTML is scraped and no access controls are bypassed; without a key, the page links to the same query on Google. Uses SerpApi because Google's Custom Search JSON API closed to new customers (ending Jan 2027).
