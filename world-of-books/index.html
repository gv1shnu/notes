The problem

Started as an assignment: browse live product data from World of Books — navigation → categories → a single book's details — backed by a real scrape, not a static dump. (The original brief has been removed from the repo.)

It grew into a full-stack explorer with background scraping, caching, pagination, typo-tolerant category search, and a later "Extract PDF" reader.

Architecture

What I observed / changed my mind on

  • The first design used a Playwright headless browser worker. Later it moved to plain HTTP + World of Books' Algolia listings — faster, lighter, and it fits in a 512 MB free instance where Chromium does not.
  • When the DB is empty, every request for navigations started a fresh scrape; concurrent requests launched several Chromiums at once and OOM'd. Fix: share one in-flight scrape and log failures instead of swallowing them.
  • Static export needs every route to be a real file, so category/product pages read their slug/id from the query string (?slug=, ?book=).
  • Render's free Postgres is deleted after 30 days, so the database lives on Neon; Render runs in Singapore next to it.
  • A good book link should survive a re-scrape, so products resolve by handle and are rebuilt from the source page if missing.

typo tolerance

Unknown category slugs 404, then the site corrects clear typos or suggests the closest categories (lib/suggest.ts, a "did you mean").
free-tier hosting with no card and no DNS changes was an explicit constraint for the Oct rework.

Spec sheet

BackendNestJS + Prisma; Redis + Bull queue; HTTP/Algolia scraper
FrontendNext.js (React Query), static export with configurable BASE_PATH
DataPostgres models: Navigation, Category, Product, ScrapeJob — with targeted indexes
CachingRedis with TTL; 1-hour staleness → background refresh
Deployfrontend on GitHub Pages, backend on Render (Docker) + Render Key Value, Postgres on Neon; a Docker-Compose + Caddy stack as a self-host alternative
