Decisions

decisionwhy
Queue scraping, don't block requestsa page load can't wait on a multi-page scrape
Stale-while-revalidate (1h TTL)fast responses, freshness restored in the background
HTTP + Algolia over a headless browserfits a 512 MB free instance; faster and lighter

Postgres on Neon, app on Render (Singapore)Render's free DB is wiped after 30 days; keep app next to the DB
Products by handlelinks survive a re-scrape; rebuilt from source if missing
PDF match by page count + tolerancea cheap, explainable heuristic; never claims it proves the edition
Share one in-flight scrapeempty-DB concurrent requests otherwise launch many browsers

How I judge it

  • Cache hit rate and response latency on category/product reads.
  • Scrape job success / retry counts (ScrapeJob log + /categories/:slug/progress).
  • Memory headroom: Chromium/scraper stays under 512 MB on the free instance.
  • PDF match quality: matched / no_match / missing_metadata / not_configured outcomes.
  • Tests: unit specs per service + a categories e2e spec.

Rebuild it from scratch

  1. Schema first
    Prisma models Navigation / Category / Product / ScrapeJob with the indexes above; docker-compose for Postgres + Redis.
  2. Scraper service
    Fetch navigation, then category pages (paginate), then product details over HTTP/Algolia; config for delays, retries, max pages.
  3. Queue
    Bull jobs for scrapes with retries + concurrency; a processor that upserts and writes a ScrapeJob log.
  4. API + cache
    NestJS controllers for categories/products; Redis TTL cache; stale-while-revalidate that enqueues a refresh.
  5. Frontend
    Next.js with React Query; static export; query-string routes; a typo-tolerant category suggester.
  6. Extract PDF
    SerpApi search → download up to 5 → pdf-lib page count → tolerance match → cache bytes → PDF.js reader via a token route.
  7. Deploy
    Pages workflow for the frontend; Render Docker + Key Value for the API; Neon for Postgres; a Caddy compose stack as a self-host option.
