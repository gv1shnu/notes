The brief

"You are allowed ONLY ONE API: POST /order." It has to check the product exists, check the stock, deduct it, create the order, never go negative, and stay safe when requests arrive at the same moment.

The brief (requirements.pdf, committed with the code) was a 3-day take-home. It was there to test API discipline and backend layering, not UI. It had hard fail conditions: more than one API, mixed layers, logic inside the controller, or stock logic in the frontend. I built it in one morning, from 08:59 to 12:27.

The edge case the brief insists on

What I observed

  • The layering is literal. routes/ → controllers/ → services/ → repositories/ → models/, matching the brief's folder list name for name. The controller only checks the request shape and maps errors to status codes.
  • Errors travel as strings. The service throws Error('PRODUCT_NOT_FOUND') / Error('INSUFFICIENT_STOCK') and the controller matches on error.message: 404 / 400, anything else 500.
  • The transaction object is passed down by hand into every repository call. That's how the read and the write share one transaction.
  • Failed orders leave no trace. Status is always 'SUCCESS', because a rejected order rolls back before its row exists.

honest gaps vs the brief

There's no Flutter client in the repo (only React). There's a GET /health probe next to the one business API. Nothing seeds the products either: sync() creates empty tables.
The README answers the brief's three questions: folder structure, API flow and concurrency handling.
